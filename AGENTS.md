# BEKHAN OS: обязательные правила развития

Система развивается как модульный монолит. Цель — небольшая стоимость сопровождения,
изолированные изменения и возможность замены источников данных без переписывания экранов.
Это требование владельца проекта, а не временная рекомендация.

## Границы

- `src/app` — композиция модулей, маршруты, оболочка. Бизнес-правила здесь не размещать.
- `src/modules/<feature>` — экран, команды, состояние и правила одного направления.
  Модуль не импортирует внутренние файлы другого модуля. Связи передаются через
  именованные публичные порты в точке сборки приложения.
- `src/shared` — общие элементы интерфейса и чистые функции. Не зависит от модулей.
- `src/platform` — хранилища и общие сервисы. Не содержит правил CRM/финансов.
- `src/integrations/<provider>` — сменные адаптеры внешнего API. Экраны не вызывают
  `fetch`, SDK, URL RPC и таблицы напрямую. Доменная модель не зависит от провайдера.
- Каждый модуль владеет своими данными. Общие показатели читаются через селекторы;
  чужие записи нельзя менять напрямую. Изменение контракта — обратно совместимое
  расширение либо новая версия с проверенным переходом.
- Предпочитать наименьшее законченное изменение. Не добавлять микросервисы, очереди,
  библиотеки и абстракции без конкретной необходимости. Изоляция не означает,
  что изменение общего контракта никогда не затронет соседний модуль.

## Заявки: неизменяемый внешний контракт

1. Лендинг `bronservis.ru` и прежнее приложение сохраняют свой маршрут. Не менять
   форму, `lead_submit`, API, БД, права, DNS, ключи и публикацию старых репозиториев
   ради подключения BEKHAN OS.
2. Рабочая CRM использует тот же российский API и существующие персональные учётные
   записи. Одна заявка имеет один UUID и видна в обоих интерфейсах. Это единая CRM,
   а не две расходящиеся копии; изменения статуса/заметки/корзины общие.
3. Использовать существующие именованные RPC. Права и отозванная сессия проверяются
   сервером. Скрытая кнопка не является защитой. Не расширять доступ `anon`.
4. При записи передавать `expected_updated_at`; конфликт нельзя затирать. Новый
   лид создаётся с одним ключом операции; после неизвестного результата повтор
   использует тот же ключ и те же данные. Не выполнять слепые повторы записи.
5. Не создавать тестовые заявки/финансовые записи в рабочей очереди. Проверки
   production — без записи: health, ping, отказ анониму, отклоняемый submit.
6. Исходный облачный проект Supabase находится INACTIVE после миграции. Не
   возобновлять его и не обращаться к его БД/REST для этой задачи.

## Данные, вход и отказоустойчивость

- В клиенте допустим только публичный URL и anon/publishable key. Запрещены
  service_role/secret key, пользовательские пароли, выгрузки и токены в git/логах.
- Рабочие заявки хранятся в памяти текущей сессии. Не включать их в демо-хранилище,
  экспорт примера, сводку ChatGPT, публичные снимки и фикстуры.
- Рабочие данные и пример — разные режимы с явной подписью. Ошибка сервера не
  переключает CRM на демо и не показывается как пустая рабочая очередь.
- Сессия BEKHAN OS имеет отдельный ключ, выход локальный: старое приложение
  продолжает работать. Не очищать его storage/IndexedDB/очереди.
- Не заменять данные до подтверждения сервера. Показывать ошибки и конфликты;
  при потере связи сохранять ввод формы. Поздний ответ после выхода игнорировать.
- Сохранять дату последнего успешного чтения, обновлять при возврате на вкладку.
  Фоновое чтение не закрывает форму и не меняет текст, который вводит человек.
- Перенос браузерных данных сохраняет прежний ключ `bekhan-os-demo-v1` и записи.
  Сброс примера не затрагивает рабочую CRM и существующее приложение.

## Проверка и публикация

`npm run verify`: проверка границ, значимые тесты, воспроизводимая сборка. Новые
зависимости фиксировать точной версией и lockfile. В git нет node_modules и
секретных конфигураций. Публикуется только собранный клиент.

Проверять ошибку/пустое состояние, доступ без входа, конфликт версии, повтор
создания, сетевой сбой и сохранность старых локальных данных. Для интерфейса —
телефон и компьютер, внутреннюю прокрутку канбана и доступные кнопки.

Решения записывать в ADR, эксплуатацию — в runbook. Различать написанный код,
опубликованную версию и подтверждённую работу с реальной учётной записью.
Не обещать полную готовность остальных модулей по одному подключению CRM.
