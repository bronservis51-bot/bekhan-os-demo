# Выпуск и сопровождение CRM

## Где что работает

- BEKHAN OS: https://bronservis51-bot.github.io/bekhan-os-demo/#/crm
- Демо CRM: тот же сайт, маршрут `#/crm/demo`.
- Лендинг: https://bronservis.ru/ — без изменений.
- База/Auth/RPC: https://api.bronservis.ru — существующий российский сервер.
- Приложение франшизы: https://app.bronservis.ru/ — без изменений.

Новые серверы, БД, тарифы, ключи доступа администратора не создавались. Подключение
BEKHAN OS — дополнительный клиент, не посредник в приёме заявок.

## Вход и работа

1. Открыть рабочую CRM; ввести существующую почту/пароль менеджера приложения
   франшизы. Саморегистрации и общего пароля нет. Права проверяет сервер.
2. Очередь загружается целиком через `lead_list`; в корзине — `lead_trash_list`.
   Подтверждённая пустая очередь отличается от ошибки чтения.
3. При работе в двух интерфейсах ожидать общие статусы/заметки/корзину. Конфликт
   версии не перезаписывается. Скопировать свой текст и открыть актуальную карточку.
4. После сетевой ошибки не создавать новую копию заявки. Повторить ту же форму;
   UUID операции сохраняется, пока открыта эта форма. Нет очереди офлайн-записей.
5. Выход очищает данные нового интерфейса и его локальную сессию; старое приложение
   остаётся со своей сессией. Не очищать его storage, IndexedDB или PWA-очередь.

## Сборка и проверка

Node 22 или новее; `npm ci`, затем `npm run verify`. `build` создаёт `dist/`
и те же `index.html`/`assets/` в корне для существующей публикации Pages main:/.
Сборка статическая; зависимости входят в собственный JS, внешнего CDN SDK нет.
В исходниках только публичные настройки `src/app/config.js`.

CI проверяет границы, тесты и воспроизводимость собранных публичных файлов.
Pages публикует существующий main:/, отдельный VPS для клиента не нужен.
Публиковать исходники и собранные assets одним commit; дождаться Pages success
именно для него. Не удалять предыдущие assets: уже открытые вкладки должны
иметь возможность загрузить CSS/модули до следующего обновления.

## Проверки российского API без записи

`npm run probe` читает текущую форму лендинга, сравнивает API и публичный ключ с
конфигурацией, затем проверяет health, ping, запрет анонимного чтения и намеренно
некорректный пустой submit, который сервер должен отклонить с validation. В отчёте
нет ключа, паролей, JWT пользователя или контактов. Корректную тестовую анкету
в рабочую очередь не отправлять.

Защищённое чтение и роли проверяются под реальной учётной записью без фиктивных
лидов. Доставку новой настоящей анкеты сверять по одинаковому UUID в двух
интерфейсах. Не выдавать проверки без входа за проверку рабочего сеанса директора.

## Если что-то не работает

- Чтение не прошло: проверить время успешного обновления, кнопку обновления,
  доступность Auth/API и срок сессии. Не переключаться молча на демо.
- Нет доступа: проверить действующую роль в прежней системе. Не расширять anon,
  не менять RLS и не создавать параллельную роль ради обхода ошибки.
- Конфликт: сохранить свой текст; перечитать и заново открыть карточку.
- Ошибка BEKHAN OS: прежний лендинг и приложение продолжают работать напрямую.
  Для отката клиента вернуть проверенную сборку в этом репозитории; БД и
  приёмник лендинга при этом не откатываются и не меняются.
- Смена API при будущей миграции: отдельный релиз конфигурации с проверкой
  парности URL/anon key, контрактов, прав и старых открытых клиентов. Публичные
  настройки не должны выбираться из непроверенного URL-параметра браузера.

Резервные копии рабочей базы обслуживаются существующей инфраструктурой.
Этот выпуск не перенастраивает их и не утверждает готовность по одному README.

Старые `app.js`, `crm.js`, `style.css` в корне временно оставлены замороженными
для кешированного HTML прежнего прототипа. Новая страница их не загружает.
Исходники для дальнейших изменений находятся только в `src/`.
