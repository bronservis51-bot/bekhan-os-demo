# ADR-0001: модульный монолит и единый источник заявок

Статус: принято. Дата: 16 ноября 2026. Требование владельца: эволюционируемость,
адаптивность, изоляция изменений и сокращение технического долга.

## Контекст

Прототип состоял из двух скриптов с общими глобальными переменными. Это связывало
экраны, формы и хранилище. Рабочие заявки уже поступают с `bronservis.ru` в
`https://api.bronservis.ru/rest/v1/rpc/lead_submit`. Действующая CRM приложения
франшизы читает их через защищённые RPC. Исходный облачный проект после миграции
имеет статус INACTIVE; для подключения нового интерфейса он не используется.

## Решение

Клиент — модульный монолит на ES modules. Отдельные модули: CRM, финансы, задачи,
сеть, контент, цели, тренировки, обзор и настройки. Каждый экспортирует фабрику
с именованными зависимостями, render/actions/forms и публичные селекторы. Модули
не импортируют внутренности друг друга. `src/app/main.js` соединяет их порты.
Общие компоненты не зависят от бизнеса. Проверка импортов входит в CI.

CRM получает `repository` и `auth`, а не SDK/URL/таблицы. Адаптер
`src/integrations/bron-leads` реализует существующие RPC/Auth российского API.
Замена провайдера требует реализации этого порта, а не переписывания канбана.
В остальных модулях порт `repository` пока реализован браузерным демо-хранилищем.
У каждого — доступ только к своим разделам. Межмодульные показатели читаются
через селекторы в точке сборки; рабочие контакты не участвуют в демо-сводках.

**Одна запись — два интерфейса.** Нового приёмника, двойной отправки, копии БД,
webhook и синхронизации между двумя CRM нет. UUID, статус, заметка и корзина общие.
Существующие лендинг, приложение, права, схема и сервер не изменяются. Отказ
BEKHAN OS не влияет на приём заявок и работу прежнего приложения.

Запись подтверждает сервер. Редактирование/перенос/корзина передают версию записи;
чужое изменение вызывает конфликт. Создание использует один UUID операции,
повтор той же формы — те же данные и тот же UUID. Автоматических повторов записи
нет. Сетевой сбой не закрывает форму и не превращается в сообщение об успехе.

Рабочие заявки живут в памяти сессии, без браузерного постоянного кеша.
Фоновое чтение — раз в 30 секунд на открытой видимой CRM, при возврате на вкладку
и восстановлении сети. Есть время успешного чтения и явная ошибка. Поздний ответ
не переходит между пользователями и не отменяет уже подтверждённую запись.

Auth использует существующие учётные записи и серверные полномочия `org.manage`.
Свой ключ хранения, по умолчанию sessionStorage, запоминание — по выбору человека.
Выход имеет scope local. Пароль не записывается в проект/хранилище; на клиенте
только публичный anon key. Исходный cloud backend не возобновляется.

## Почему не альтернативы

- Двойная отправка формы создаёт частичные доставки и требует разбирать дубликаты.
- Вторая база и webhook добавляют очередь, повторы, сверки и эксплуатационные расходы.
- Микросервисы для небольшого кабинета увеличивают число развёртываний и отказов.
- Полная смена UI-фреймворка сейчас не помогает подключить заявки и повышает риск.
- Сохранение общих глобальных скриптов оставляет изменения неявно связанными.

## Ограничения и дальнейшая эволюция

Рабочим подключён только модуль CRM. Другие модули остаются явным примером;
полный релиз персональных финансов/задач требует собственного серверного хранения
и согласованных прав. Наличие входа CRM не делает остальные записи общими.

Старый локальный ключ и данные сохраняются. Нет автоматического импорта демо
в рабочую CRM. Подключение следующего модуля — новый адаптер его repository,
контракт, проверки прав и отдельный переход, без замены приёмника лендинга.

Общий компонент или контракт может затронуть несколько модулей. Изоляция
контролируется зависимостями и тестами; обещания абсолютной независимости нет.
Исторические старые root-скрипты удалены из исполнения; публикуется проверяемая
сборка, а исходники и lockfile остаются в репозитории.
